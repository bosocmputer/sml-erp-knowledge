## 1. ข้อเท็จจริงที่ทีมใช้ (ตรวจ 2026-10-21/22)
**โค้ด sml_mcp_ai (`~/dev/smlmcpconnect`, commit 793c293):**
- F1 **ไม่มีการยืนยันตัวตนบน HTTP** — role มาจาก header `mcp-access-mode` ที่ client ส่งเอง (`src/index.ts` ~302, ~357, ~417); ไม่พบ API key / `Authorization` ⇒ ใครเข้าถึง port ได้ ประกาศตัวเป็น `admin` ได้
- F2 `POST /reload` และ `POST /call` อยู่บน HTTP เดียวกัน ไม่มีการป้องกันเพิ่ม (`src/index.ts` ~286, ~490)
- F3 **database เดียว** — `getPool()` singleton, config `DB_NAME` เดียว (`src/utils/database.ts`, `src/config/loader.ts`) ⇒ ยังไม่รองรับหลายร้าน/หลาย provider
- F4 เครื่องมือเขียนมีตัวเดียว `create_sale_reserve` → `SMLJavaRESTService/restapi/salereserved` (`src/tools/write/create-sale-reserve.ts` ~92)
- F5 database ถูกเปิดแบบ READ ONLY ทุก query ตามเอกสารโปรเจกต์ (ทุก tool อ่านอย่างเดียว ยกเว้น F4 ที่ไปทาง REST)

**ความรู้ SML (vault):**
- F6 คะแนนความรู้ถ่วงน้ำหนัก ≈ 75/100 ([[00-Gap-Review]]); ระบบหลักของร้าน POS Professional ราว 80–90
- F7 สเปกการเขียนที่ **ยืนยันด้วย SQL จริงแล้ว**: ใบสั่งขาย (สร้าง/จากใบเสนอราคา/แก้/ยกเลิก), บิลขายสด/เชื่อจาก SO, ยกเลิกบิล, ใบวางบิล, รับชำระ (เงินสด/โอน/ตามใบวางบิล), รับคืนเชื่อ, ซื้อเชื่อ, จ่ายชำระเงินสด, สร้างสินค้า ([[runtime-verified]])
- F8 ยังไม่ยืนยัน: ลดหนี้ไม่กระทบสต็อก, บัตร/เช็ค, ใบสั่งซื้อ→รับสินค้า, ลบเอกสาร ฯลฯ ([[00-Unverified]])
- F9 **ต้นทุนถูกคำนวณเฉพาะเมื่อมีโปรแกรม SML ของร้านนั้นเปิดอยู่** (คิว `process`); `kbgtest` ค้าง 10 แถวตั้งแต่ 2026-10-16 ([[stock-cost]])
- F10 เลขที่เอกสารไม่มีการล็อก ใช้ unique `(doc_no, trans_flag)` กันซ้ำ ([[write-spec-sale-order]] §1)
- F11 เอกสารสินค้า**ไม่ตรวจงวดปิดตอนบันทึก** ([[tax-period]] §3); บิลยกเลิกยังลง GL ถ้ารูปแบบ 45 ไม่มี `gl_book` ([[write-spec-cancel]])
- F12 มีหลายระบบเขียน DB ของ SML ตรงอยู่แล้ว (sml-api-bybos, nextloyalty-api เขียน `ar_customer.website`) ([[server-layout]])
- F13 บน server ทดสอบ **ไม่มี container SMLJavaRESTService** ([[server-layout]]) ⇒ F4 ใช้ไม่ได้บน deployment นี้
- F14 ตัวเลือกร้านต่างกันมาก (VAT 10% / หลายสกุลเงินที่ thao_auto, ทศนิยม 0–7, ตรวจวงเงิน) ([[tenants-overview]] §4)
- F15 การแก้ไขเอกสารของ SML = ลบแล้วใส่ใหม่ `roworder` เปลี่ยน; มีล็อก `guid_code` ([[document-engine]])

**สิ่งที่ทีมยังไม่รู้ (ต้องระวังในการตัดสินใจ):**
- U1 ร้านลูกค้าจริงแต่ละร้าน deploy แบบเดียวกับ server ทดสอบหรือไม่ (โหมดคิวต้นทุน, มี REST service หรือไม่)
- U2 จำนวนร้านที่จะใช้ช่วงแรก และใครเป็นผู้ใช้ (เจ้าของร้าน / พนักงาน / ระบบอื่น)
- U3 sml_mcp_ai ตอนนี้ deploy อยู่ที่ไหน เปิด port ออกนอกหรือไม่ (มีบันทึกว่า web service เปิดผ่าน port forwarding — sml_mcp_ai ยังไม่ได้ตรวจ)

## 2. การอภิปราย (สรุปตามบทบาท)
- **Security:** F1+F2 คือ blocker ระดับวิกฤต — ถ้า HTTP เปิดออกนอก ใครก็อ่านต้นทุน/ข้อมูลลูกค้าในบทบาท admin ได้ทันที ต้องปิดก่อนเรื่องอื่นทั้งหมด แม้จะเป็นแค่อ่านอย่างเดียว
- **Tech Lead:** F3 ต้องแก้ก่อนขาย multi-shop; tenant = (provider, data_code) ตาม [[tenants-overview]] ไม่ใช่ชื่อ database เดียว; F4 พิงบริการที่ไม่มีบน deployment จริง (F13) ⇒ ไม่ควรเป็นทางหลัก เส้นทาง ADR-001 (เขียน DB ตรงตามสเปก + doc flow + คิว) ตอนนี้มีสเปก verified พอสำหรับเอกสารชุดแรกแล้ว
- **SML Specialist:** ยืนยันว่า F7 พอสำหรับ "ขายเชื่อครบวงจร" (สั่งขาย → บิล → วางบิล → รับชำระ) แต่ต้องทำตามรายละเอียดเล็ก ๆ ทุกข้อ (`bill_type`, `ref_row`, doc flow, ค้างส่ง, ล็อก `guid_code`) — พลาดข้อเดียว รายงาน SML จะไม่ตรง
- **BA บัญชี:** F11 อันตรายต่อบัญชี — API ต้องตรวจงวดเองแบบเข้มกว่าโปรแกรม และต้องแจ้งเรื่องบิลยกเลิกไม่กลับรายการ GL; F14 ห้าม hard-code VAT/ทศนิยม
- **Backend:** งาน auth + tenant + write engine กลาง (เลขที่/retry, doc flow, สต็อกส่วน 1, คิว, logs) คืองานหลัก; สเปกแต่ละเอกสารแค่เติม mapping
- **AI Engineer:** agent ห้ามเขียนตรง — ต้อง preview + confirmation token (ADR ข้อ 2); เครื่องมืออ่านปัจจุบันใช้ได้ดี ควรเพิ่ม "เตือนเมื่อข้อมูลอาจไม่ตรงรายงาน" (เช่น กำไรเมื่อคิวต้นทุนค้าง F9)
- **QA:** ต้องมี parity test: ให้ API สร้างเอกสาร แล้วเทียบแถวกับเอกสารที่โปรแกรม SML สร้างใน capture (คอลัมน์ต่อคอลัมน์) + เปิดรายงาน SML ว่าตรง ก่อนเปิดแต่ละประเภท
- **DevOps:** ต้องมี audit log ของ API แยกจาก SML, ตัวชี้วัด (คิวต้นทุนค้าง, เลขชน, error ต่อ tenant), kill-switch ปิดการเขียนรายร้าน, rollback = ยกเลิกเอกสารแบบ SML (สร้าง 45/37) ไม่ใช่ลบแถว
- **Customer Success:** F9 จะกลายเป็นตั๋ว support ("กำไรไม่ขึ้น") ถ้าร้านไม่ได้เปิดโปรแกรม — ต้องมีทางสำรองหรือแจ้งสถานะในคำตอบ; ร้านแรกควรเป็นร้านที่ทีมเข้าถึงได้และยอมให้ capture
- **PM:** คุณค่าที่ส่งได้เร็วสุดคือ "อ่านอย่างปลอดภัย" (ถามยอดขาย/สต็อก/ลูกหนี้) — ปล่อยได้ทันทีหลังปิด F1–F3; การเขียนให้เริ่มที่สายขายเชื่อกับร้าน pilot 1 ร้าน

## 4. ข้อสรุป
**คำตอบต่อคำถาม "พร้อม prod ไหม":** ❌ **ยังไม่พร้อม** — ไม่ใช่เพราะความรู้ SML ไม่พอ (สายขายเชื่อพร้อมแล้ว) แต่เพราะ **ช่องโหว่ auth (F1/F2) และยังไม่รองรับหลายร้าน (F3)**

ลำดับที่ทีมตกลง (ไม่ระบุวันที่ เพราะยังไม่ได้ประเมินเวลาของทีมจริง):
| เฟส | งาน | เกณฑ์ผ่าน (Definition of Done) |
|---|---|---|
| **0 ความปลอดภัย** | API key ต่อ client, role ผูกกับ key ฝั่ง server, ปิด/ป้องกัน `/reload`, ตรวจว่า port เปิดที่ไหน (U3), log ไม่มี secret | ทดสอบส่ง `mcp-access-mode: admin` โดยไม่มี key แล้วถูกปฏิเสธ |
| **1 อ่านอย่างปลอดภัย (prod แรก)** | multi-tenant (provider + data_code), เครื่องมืออ่านปัจจุบัน, เตือนเมื่อข้อมูลอาจไม่ตรงรายงาน (คิวต้นทุนค้าง, เอกสารลงวันที่ล่วงหน้า) | ตัวเลขยอดขาย/ลูกหนี้/สต็อกตรงกับรายงาน SML ใน pilot |
| **2 write engine กลาง** | เลขที่ + retry เมื่อชน unique, ตรวจงวด, ตรวจล็อก `guid_code`, doc flow, สต็อกส่วน 1, คิว `process`, `logs`/`erp_logs`, idempotency, audit, kill-switch | unit + integration test ผ่านใน AOY |
| **3 เขียนสายขายเชื่อ (ทีละตัว)** | ใบสั่งขาย → บิลจาก SO → ใบวางบิล → รับชำระ | parity test คอลัมน์ต่อคอลัมน์กับ capture + รายงาน SML ตรง |
| **4 ขยาย** | ทดสอบรอบ 5 แล้วค่อยเปิดลดหนี้/บัตร-เช็ค/ซื้อ | ตาม [[00-Unverified]] |
